关于 GrayLog 和 Elk

ELK 的问题：

  • 多行日志处理不足： ELK 无法很好地处理多行日志，例如 Mysql 慢查询或 Tomcat/Jetty 应用的 Java 异常打印。

  • 原始日志保存不足： ELK 无法保留原始日志，只能将其分字段保存，导致搜索结果呈现为一堆 Json 格式文本，难以阅读。

  • 不匹配正则表达式的日志行丢失： ELK 对于不符合正则表达式匹配的日志行，会被全部丢弃。

GrayLog 的优势：

  • 一体化方案： GrayLog 是一体化方案，安装方便，无需解决 ELK 中 3 个独立系统间的集成问题。

  • 采集原始日志： GrayLog 能够采集原始日志，并可以事后再添加字段，例如 http_status_code、response_time 等。

  • 自定义日志采集脚本： GrayLog 允许开发者自行开发日志采集脚本，并使用 curl/nc 将其发送到 Graylog Server。这些脚本可以使用自定义的 GELF（Graylog Extended Log Format），而 Fluentd 和 Logstash 也提供了相应的输出 GELF 消息的插件。实际上，只需使用 inotifywait 监控日志的 modify 事件，并使用 curl/netcat 将新增行发送到 Graylog Server 即可。

  • 搜索结果高亮显示： GrayLog 的搜索结果能够高亮显示，类似于 Google 搜索。

  • 简单搜索语法： GrayLog 的搜索语法简单易懂，例如：source:mongo AND response_time_ms:>5000，避免直接输入 Elasticsearch 搜索 JSON 语法。

  • 导出搜索条件为 Elasticsearch JSON 文本： GrayLog 允许用户将搜索条件导出为 Elasticsearch 的搜索 JSON 文本，方便直接开发调用 Elasticsearch REST API 的搜索脚本。

GrayLog 简介

GrayLog 是一个轻量型的分布式日志管理平台，一个开源的日志聚合、分析、审计、展示和预警工具。在功能上来说，和 ELK 类似，但又比 ELK 要简单轻量许多。依靠着更加简洁，高效，部署使用简单的优势很快受到许多公司的青睐。

流程如下：

  • 微服务中的 GrayLog 客户端发送日志到 GrayLog 服务端

  • GrayLog 把日志信息格式化，存储到 Elasticsearch

  • 客户端通过浏览器访问 GrayLog，GrayLog 访问 Elasticsearch

MongoDB 是用来存储 GrayLog 的配置信息的，这样搭建集群时，GrayLog 的各节点可以共享配置

    • e GRAYLOG_WEB_ENDPOINT_URI：对外开放的 API 地址

    • e GRAYLOG_ROOT_PASSWORD_SHA2：密码加密后的密文。明文是 admin，账户也是 admin

    • e GRAYLOG_ROOT_TIMEZONE=“Asia/Shanghai”：GrayLog 容器内时区

    • e GRAYLOG_MONGODB_URI：指定 MongoDB 的链接信息

Lookup table

Lookup table 允许查找/映射/转换消息字段值为新值，并将它们写入新消息字段或覆盖现有字段。

简单来说，Graylog 的 Lookup Table（查询表） 就像是给你的日志系统装了一个 实时翻译器 或 自动备注 功能。

在处理日志时，很多原始数据是冷冰冰的代码（如 IP 地址、用户 ID、状态码），Lookup Table 的作用就是在日志进入 Graylog 的那一刻，自动根据这些代码去查表，把更易读的信息补全到日志里。

Lookup table 功能主要由三部分组成

  • Data Adapter (数据适配器)：告诉 Graylog 去哪里找数据。可以是 CSV 文件、数据库（MySQL/MongoDB）、甚至是网络 API。

  • Cache (缓存)：查过的数据存入内存，不用每次都去翻文件或查数据库，极大提升速度。

  • Lookup Table (查询表实体)：一个逻辑外壳，把“适配器”和“缓存”组合在一起，起个名字供后续调用。

Pipeline

Pipeline 的概念

Pipeline 是 Graylog 中一套基于 逻辑规则 的处理器。它允许你通过编写简单的代码（规则），对进入系统的每一条日志进行精准的“手术”。

一条日志进入 Graylog 后，会像水流一样流过这个管道，管道里的各个“工序”（Rules）会依次决定：

  • 这条日志要不要丢弃？

  • 这个字段要不要改名？

  • 要不要根据内容加个标签？

  • 要不要去翻一下“查询表”补全信息？

Pipeline 的作用

  • 条件路由（它可以根据内容决定日志的去向）

    • 例子 ：如果日志级别是Error，就把它分流到“紧急关注”流；如果是Debug，就直接丢弃以节省空间。

  • 数据转换（它可以把杂乱的数据整理干净）

    • 例子 ：原始日志里的时间格式不对，Pipeline 可以把它统一转换成标准格式。或者把Response_Time: 500ms里的ms去掉，转成纯数字以便计算。

  • 动态计算（它可以做简单的加减乘除或逻辑判断）

    • 例子 ：如果request_size大于 10MB，就自动加一个big_payload: true的字段。

  • 调用工具（这就是它和 Lookup Table 的关系）

    • Pipeline 本身并不存储大量数据，当它遇到需要“翻译”的字段时，它会 主动去查 Lookup Table。

Pipeline 和 Lookup Table 的区别

特性Pipeline (管道)Lookup Table (查询表)
比喻加工逻辑（工人）数据仓库（字典）
解决的问题“我要怎么处理这条日志？”“这个代码代表什么意思？”
例子如果是登录日志，就去查姓名。101 -> 张三
代码表现if (has_field("ip")) { ... }一个存储了成千上万 IP 的 CSV 或数据库。

创建 IP 地址解析的 Pipeline

创建对应的解析规则，如下：

rule "MyLookIP GeoIP enrichment New"
when
   has_field("LOGIN_IP")
then
   // 执行自定义IP查询
   let geo = lookup("MyLookIP", to_string($message.LOGIN_IP));
   
   // 获取基础地理信息字段
   let country = geo["country"];
   let province = geo["province"];
   let city = geo["city"];
   let district = geo["district"];
   let latitude = geo["latitude"];
   let longitude = geo["longitude"];    
   
   // 合并字段
   let full_geo_info = to_string(country) + ", " + to_string(province) + ", " + to_string(city) + ", " + to_string(district);

   // 设置合并后的字段
   set_field("src_ip_geo_full", full_geo_info);

   set_field("latitude", latitude);    
   set_field("longitude", longitude);    

end

Message Processors

注意，如果上面没有解析成功，可能和 Message Processors Configuration（消息处理器配置）的配置有关。它定义了日志进入 Graylog 后的处理顺序。

  • AWS Instance Name Lookup

    • 专门针对亚马逊 AWS 的。如果你的日志来自 AWS，它会自动去查这个实例叫什么名字

  • Message Filter Chain（消息过滤器链）

    • 这是处理 Extractors（提取器） 的地方。如果你在 Input 界面配了简单的正则提取，就在这一步执行。

  • Stream Rule Processor（流规则处理器）

    • 决定日志该归类到哪个 Stream（流） 。比如判断日志是不是属于“防火墙日志流”

  • Pipeline Processor（管道处理器）

    • Pipeline 执行的地方，，意味着 Pipeline 可以使用前面步骤已经提取好的字段

  • GeoIP Resolver

    • 把 IP 地址转换成地理位置（城市、国家）
